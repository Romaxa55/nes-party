# nes-party

Веб-версия NES, в которую можно играть вдвоём через браузер с телефонов — каждый
у себя, через интернет.

Сейчас в репозитории **этап 1: бенчмарк ядра эмуляции**. Прежде чем строить
сетевую часть, надо ответить на один вопрос: тянет ли обычный телефон эмуляцию
NES на JavaScript в стабильные 60 кадров. От ответа зависит вся дальнейшая
архитектура — хватит ли JS-ядра или сразу нужен libretro-кор в WASM.

## Запуск

```bash
npm install
npm run dev
```

Vite поднимется с `--host`, поэтому в выводе будет два адреса: `Local` для
компьютера и `Network` вида `http://192.168.1.167:5173/`. Второй открывается
с телефона, если тот в той же сети Wi-Fi.

Дальше нужен образ игры — файл `.nes`. В репозитории его нет и не будет:
образы игр защищены авторским правом, поэтому файл выбирается на устройстве
и никуда не отправляется. Он остаётся в браузере (`localStorage`), чтобы при
повторном открытии не искать его заново.

## Что меряется

Замер идёт четырьмя этапами, каждый — 180 кадров прогрева плюс 600 кадров
замера, чтобы JIT успел прогреться и цифры не врали:

| Этап | Смысл |
| --- | --- |
| Ядро | голые CPU и PPU без звука и отрисовки |
| + звук | разница показывает цену эмуляции APU |
| + рендер | разница показывает цену конвертации кадра и `putImageData` |
| Полный цикл | то, что реально происходит в игре — главная цифра |

Отдельно меряется снимок состояния (`toJSON`/`fromJSON`) — от него зависит,
возможен ли роллбэк-нетплей.

Во время замера эмулятор сам нажимает Start и A, чтобы проскочить заставку:
на статичном логотипе PPU рисует заметно меньше, и результат вышел бы
оптимистичнее реальности.

Показываются средние, p95 и худший кадр. Средние обманчивы — игру портят
именно редкие тяжёлые кадры, поэтому вердикт выносится по p95.

**Живой режим** — отдельная кнопка. Автозамер меряет чистое процессорное время
`nes.frame()`, а живой режим показывает реально достижимый FPS через
`requestAnimationFrame`: туда входит композитинг браузера, троттлинг и всё
остальное, что чувствует игрок. Разница между двумя цифрами бывает
кратной, поэтому смотреть надо на обе.

## Что уже выяснилось

Снимок состояния в jsnes весит около **1.2 МБ** и снимается за **6.5 мс**
даже на быстрой машине. Для роллбэк-нетплея снимок нужен каждый кадр, то есть
почти 40% кадрового бюджета уходило бы впустую ещё до самой игры. Причина в том,
что `toJSON` тащит развёрнутые кэши тайлов, хотя настоящее состояние NES —
единицы килобайт.

Вывод: роллбэк на jsnes «как есть» построить нельзя. Сетевую часть строим на
задержке ввода (delay-based), а к роллбэку возвращаемся только если состояние
будет переписано на плоский `ArrayBuffer`.

## Куда это идёт дальше

Играем удалённо, поэтому архитектура — **host-authoritative**: один узел гоняет
эмулятор и раздаёт картинку через WebRTC video track, остальные шлют только
нажатия по DataChannel. Рассинхронизация при такой схеме невозможна в принципе,
образ игры нужен только хосту, а клиентом может быть сколь угодно слабый телефон.

Дальнейшие этапы:

1. Звуковой конвейер через `AudioWorklet`.
2. Signaling-сервер и комнаты по короткому коду.
3. WebRTC: видео от хоста, ввод от клиентов.
4. TURN-сервер — без него часть NAT-конфигураций не соединяется.
5. PWA, блокировка ориентации, деплой.
